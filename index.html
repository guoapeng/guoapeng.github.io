1.1 Docker Compose 是什么？

Docker Compose 是用于定义和运行多容器 Docker 应用的工具。它通过一个声明式的 YAML 文件（通常命名为 compose.yaml 或 docker-compose.yml），描述应用由哪些服务（services）、网络（networks）、卷（volumes）等组成，然后用一条命令即可创建、启动、停止或销毁整套环境。

Nezha 哪吒监控 v2 安装与配置教程：从零部署到服务器接入

一、前言

如果你同时管理着几台、十几台甚至更多 VPS，最头疼的往往不是“机器挂了”，而是“挂了却不知道”。打开一堆终端、一个个 htop 或 uptime，效率低下；等到发现某个站点打不开，可能已经过去好几个小时。有没有一个轻量、集中的方式，把所有服务器的状态、流量、可用性都放在一个页面里看？这就是哪吒监控（Nezha）要解决的问题。

1.1 Nezha 是什么

Nezha（哪吒监控）是一个轻量的服务器与服务监控工具。它由两部分组成：面板（Dashboard）负责展示数据、管理节点和发送告警；Agent 安装在被监控的机器上，负责采集系统信息并上报。整体设计简洁，部署门槛不高，适合个人站长和运维新手使用。

1.2 v2 版本的主要特点

v2 是一次较大的重构版本，与 v1 在架构和通信方式上都有明显变化。主要特点包括：

  • 整体架构重构，面板与 Agent 的职责划分更清晰。
  • 面板与 Agent 之间改用 gRPC 通信，后续配置反向代理时需要注意对 gRPC 的支持（具体写法后文会讲）。
  • 界面和交互有所改进，日常查看状态更顺手。
  • 功能上对告警、服务探测等能力做了调整与增强。
  • 安装与配置流程相对 v1 有所简化，但与 v1 不兼容。

需要特别提醒：v2 与 v1 不能原地升级。已有 v1 环境的读者，请先阅读本教程中关于迁移的章节，再决定如何处理旧数据与旧节点。

1.3 适用场景

  • 多台 VPS 需要统一查看 CPU、内存、磁盘、流量等基础状态。
  • 希望对 HTTP/HTTPS 服务做简单可用性探测。
  • 需要在服务器离线或关键指标异常时及时收到通知。
  • 个人或小团队希望用一套轻量工具完成基础运维监控，而不想引入过重的监控体系。

1.4 本文将完成什么

本教程将按以下顺序带你完成一次完整部署：

  1. 部署 Nezha v2 面板
  2. 配置反向代理与 HTTPS
  3. 在被监控机器上安装 Agent
  4. 配置通知与告警

1.5 阅读提示

本文测试环境为：Debian 12 / Nezha v2.x.x / 测试时间 2026-10（具体版本号与官方文档为准）。文中出现的 your.domain.com、your-email@example.com 等均为占位符，请替换为你自己的域名和邮箱。命令与配置以实际环境为准，遇到差异时请优先参考官方文档。

接下来我们先从准备工作开始。

二、准备工作

正式动手前，先把环境和前置条件理顺。准备得越扎实，后面安装、反代、上线 Agent 就越少踩坑。本章只做准备工作，不涉及具体安装命令。

2.1 环境要求

面板服务器

面板（Dashboard）需要一台能从公网访问的服务器。推荐使用较新的稳定发行版，例如 Debian 12 或 Ubuntu 22.04 LTS。内存与磁盘没有特别严苛的硬性门槛，普通轻量 VPS 即可满足个人或少量节点的使用，具体建议以官方文档（nezha.wiki）为准。

必须具备公网 IP，否则外部无法访问面板，Agent 也无法正常上报。若服务器在内网或仅有私有 IP，需要额外做端口映射或隧道，本教程默认你使用带公网 IP 的 VPS。

被监控机器（Agent 端）

Agent 支持在多种系统和架构上运行。官方文档覆盖的主要平台如下（以实际发布和支持情况为准）：

系统常见架构说明
Linuxx86_64、ARM 等最常用，一键脚本支持较好
Windowsx86_64支持一键安装
macOS官方文档已覆盖适合少量桌面/测试机

更多特殊环境（如 OpenWrt、群晖等）可参考官方文档的对应章节。架构与系统支持列表以 nezha.wiki 最新说明为准。

典型拓扑

面板和 Agent 不必在同一台机器上。常见做法是：

  • 一台专门的 VPS 跑面板（带域名、反向代理和 HTTPS）
  • 其他需要监控的 VPS / 机器只安装 Agent，向面板上报数据

也可以把面板和一台 Agent 装在同一台机器上，适合节点很少的情况。

2.2 域名准备与 DNS 解析

虽然可以直接用 IP + 端口访问面板，但强烈建议使用域名，原因很简单：

  • 方便配置 HTTPS（证书通常按域名签发）
  • 反向代理时更清晰
  • 以后更换服务器 IP 时，只需改 DNS，已安装的 Agent 不用批量改配置

在域名服务商处添加一条 A 记录（IPv4）或 AAAA 记录（IPv6），指向你的面板服务器公网 IP。示例：

  • 主机记录：dashboard（或你喜欢的子域名）
  • 记录类型：A
  • 记录值：your_server_ip

最终完整域名形如 dashboard.your.domain.com。

2.3 端口规划与防火墙

哪吒 v2 面板默认将 Web 访问与 Agent 通信放在同一端口上（官方文档中的默认值为 8008，具体以你安装时选择或官方最新说明为准）。反向代理后通常只对外暴露 80/443。

2.4 是否使用 Cloudflare / CDN

v2 面板与 Agent 通过 gRPC 通信。CDN（尤其是 Cloudflare 的代理模式）对 gRPC 和长连接的支持并不总是开箱即用，容易导致 Agent 上线异常或数据上报不稳定。

给新手的建议：

  • 第一次部署时，先把域名设为 仅 DNS 解析（灰云），不开启代理。
  • 确认面板能正常访问、Agent 能稳定上线后，再考虑是否启用 CDN 以及如何正确配置 gRPC 相关规则。
  • 详细的反向代理与 CDN 配置会在第四章展开。

如果暂时只用 IP 访问也可以，但后续申请证书和更换服务器会麻烦一些，仍建议尽早准备域名。

2.5 准备清单（Checklist）

进入下一章前，请确认以下事项都已完成：

  • 面板服务器已准备好，有公网 IP，系统为较新的 Debian / Ubuntu 等
  • 域名已添加 A/AAAA 记录，指向面板服务器 IP
  • 用 ping 或 dig 验证解析正确
  • 系统防火墙已放行必要端口
  • 云服务商安全组已同步放行对应端口
  • （可选）决定是否暂时关闭 CDN 代理，仅使用 DNS 解析

三、安装面板

准备工作完成后，就可以开始安装哪吒监控的面板（Dashboard）了。本章只覆盖面板本身的安装与验证，反向代理、HTTPS 和 Agent 安装会放到后面章节。

  • 选 Y：Agent 会通过 TLS 连接面板（对应配置里的 tls: true）。适用于面板前面已经有 HTTPS 反向代理、或使用 CDN 终结 TLS 的情况。
  • 选 N：明文连接（tls: false）。适用于直接用 IP:端口 或还没上 HTTPS 的情况
  • 安装面板时建议直接选 N, 因为现在还只是临时用 IP + 端口访问，还没配域名和 HTTPS。选错了会导致后面 Agent 连不上。以后随时可以在面板「系统设置」里改。

注意：

  • 安装过程需要 root 权限。端口请与第二章防火墙、安全组规划保持一致，避免装完却访问不了。
  • 端口默认常见为 8008

四、配置反向代理与 HTTPS

面板已经能通过 IP 临时访问，但生产环境更推荐用域名 + HTTPS。本章重点是把反向代理配好，让浏览器访问和 Agent 的 gRPC 通信都能正确转发。这一步最容易踩坑，请按顺序仔细操作。

4.1 为什么需要反向代理

反向代理主要解决三件事：

  1. 域名访问：用 https://your.domain.com 代替 http://IP:端口，更规范也更安全。
  2. HTTPS 加密：浏览器与面板之间的流量加密，避免明文传输。
  3. gRPC 转发：v2 的面板与 Agent 通过 gRPC 通信，反向代理必须正确转发这类流量，否则 Agent 无法上线。

4.5 使用 Cloudflare 时的注意事项

若域名接入 Cloudflare：

  • Cloudflare代理模式会对 gRPC 有影响。需要在 Cloudflare 后台开启 gRPC 支持（具体开关名称与路径以 Cloudflare 当前界面为准）。
  • Agent 使用的端口必须在 Cloudflare 支持代理的端口范围内，否则建议改用仅 DNS。

两种常见策略：

  1. Agent 通信使用仅 DNS模式：面板访问域名可以使用代理模式，Agent 对接地址用另一个仅 DNS 解析的域名或直接 IP，稳定性更高。
  2. 统一代理模式：开启 gRPC，并确保使用 Cloudflare 支持的端口，同时 SSL/TLS 加密模式建议选「完全（严格）」。

注意：SSL/TLS 模式选「灵活」容易导致证书或回源异常，生产环境不推荐。

4.8 常见问题速查

  • 证书申请失败：域名未解析、80 端口不通或被占用。检查解析与防火墙后重试。

六、安装 Agent 并添加服务器

面板侧地址与反向代理已经就绪，这一章把第一台被监控机器真正接上线。装成功后，你就能在后台和前台看到实时的 CPU、内存、磁盘和网络数据——这也是检验第四、五章配置是否正确的关键一步。

6.1 Agent 工作原理简述

Agent（探针程序）安装在你要监控的那台机器上，由它主动连接面板，并周期上报系统状态。面板根据安装命令里的连接密钥（与当前登录用户绑定）识别是谁的 Agent；连接成功后，后台会出现对应的服务器记录。

Agent 连接的目标，就是第五章在系统设置里填写的 Agent 对接地址（域名或 IP + 端口）。这个地址或端口写错、TLS 开关与实际不一致、gRPC 没正确转发，都会表现为一直离线。

6.2 在面板中获取安装命令

v2 推荐流程是：先确认 Agent 对接地址已保存，再到服务器页复制一键安装命令；Agent 连上后，列表里会出现新服务器，再编辑名称、分组等即可。

  1. 登录后台，进入 服务器 页面。
  2. 点击 安装命令（或同类入口），选择目标系统（Linux / Windows / macOS 等）。

6.6 Agent 的配置、升级与卸载

配置

一键安装后，Agent 会在本机生成配置文件（常见路径示例：/opt/nezha/agent/config.yml，以实际为准【待核实】）。也可在后台服务器列表中通过编辑配置下发部分选项。常见相关项包括连接地址 server、密钥 client_secret、是否 TLS、是否自动更新等，完整字段见官方 Agent 配置。

升级

默认情况下 Agent 会自动更新。若关闭了自动更新，可在后台对指定服务器执行 强制更新（若同时禁用了强制更新，则该操作无效）。也可按官方文档手动替换二进制后重启服务。

卸载（Linux 常见写法，以官方文档为准）

Windows 可在安装目录执行类似的 nezha-agent.exe service uninstall（以实际程序名为准）。

注意
卸载本机 Agent 后，面板里的服务器记录不会自动消失，需要你在后台手动删除；否则会留下一条离线记录。

6.7 批量添加多台服务器的建议

  • 先在一台机器上完整跑通：安装 → 在线 → 数据刷新正常，再复制同一套流程到其它机器。
  • 每台机器各自在面板复制一次安装命令并在本机执行，不要多机共用同一条已跑过的历史命令当「模板乱贴」。
  • 命名建议带用途或地区，例如 hk-web-01、jp-db-02，并善用分组，方便前台按组浏览。
  • 需要「重装并继承原记录」时，可按官方说明在安装命令中附带该服务器的 UUID（见官方 Agent 文档中的 UUID 相关说明），并先卸掉旧 Agent，避免重复注册。

6.8 常见问题速查

  • Agent 一直离线
    优先看本机日志，再测能否访问面板域名；仍不行则回查第四章 gRPC/反代与第五章 Agent 对接地址、TLS。详见第十章。

  • 安装命令执行失败
    多为网络拉不下脚本、权限不足或系统架构不匹配。检查网络与 root/管理员权限。详见第十章。

  • 数据异常或时间相关报错
    检查被控端系统时间是否同步。详见第十章。

  • 重复安装出现多条记录
    同一台机多次安装且未带原 UUID 时可能产生新记录；卸掉多余 Agent，面板侧删除多余条目。详见第十章。

  • 走了 Cloudflare 橙云后连不上
    Agent 通信对 CDN/代理较敏感，需确认端口与协议是否被支持，并对照第四章 4.5。详见第十章。
